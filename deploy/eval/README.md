# 评测工具集：召回率 / 问答准确率 / 工具调用成功率

三个指标对应三段独立的链路，**必须分开测**。混在一起测，数字不可解释。

| 指标 | 测的是哪一段 | 数据来源 | 脚本 |
|---|---|---|---|
| 召回率 | 向量检索器本身（不含大模型） | Chroma 检索结果的 `metadata.source` | `eval_retrieval.py` |
| 工具调用成功率 | Agent 执行工具的过程 | 中间件写入的 `[ToolCall]` 日志 | `eval_agent.py` |
| 问答准确率 | 端到端最终答案 | SSE 返回的答案 + LLM 裁判打分 | `eval_agent.py` |

---

## 0. 前置条件

```bash
docker compose up -d          # 容器需在运行
docker ps | grep smart_agent_backend
```

## 1. 知识库入库（必须先做）

**这是当前项目的最大缺口**：`data/` 下有 6 份知识文档，但代码里没有任何 TXT/PDF
切片入库的实现，`data/chroma_db` 目录也不存在。也就是说 Chroma 集合是空的，
`rag_summarize` 只会返回"根据现有知识库未找到相关信息"——**不补这一步，召回率恒为 0**。

```bash
bash deploy/eval/run_eval.sh ingest
```

脚本做四件事：TXT/PDF 解析 → 500 字分块（重叠 80 字）→ 通义 `text-embedding-v4` 向量化 →
写入 Chroma（`metadata.source` = 文件名，这是召回率的判定依据）。每次运行会先清空集合，可重复执行。

## 2. 召回率

```bash
bash deploy/eval/run_eval.sh retrieval
```

输出 `Recall@1 / Recall@3 / Recall@5` 与 `MRR@K`：

- **Recall@K（Hit Rate）**：top-K 结果里出现期望来源文档，记 1。
- **MRR@K**：第一条命中结果的排名倒数（第 1 名 1.0，第 2 名 0.5）。命中但排得靠后，MRR 会掉——它反映排序质量。

> `Recall@3` 对应线上 `rag_top_k=3`，是**可以写进简历的那个数**。`@5` 用来判断是"没检索到"还是"检索到了但排序靠后"。

## 3. 问答准确率 + 工具调用成功率

```bash
bash deploy/eval/run_eval.sh agent
```

逐条提问走真实 SSE 链路，同时做三件事：

1. 提问前后记录日志行号，只解析该区间的 `[ToolCall]` 行 → 得到本次调用了哪些工具、成功与否
2. 用 `qwen3-max` 作裁判，对照参考答案给 0/1 分
3. 汇总三个比率（**注意它们不是一回事**）：

| 名称 | 口径 | 说明 |
|---|---|---|
| 工具选择准确率 | 实际调用的工具集合 == 期望集合 | 衡量"选没选对工具" |
| 工具调用成功率 | 未抛异常的调用 / 总调用 | 即中间件日志里没有 `!!` 的比例 |
| 工具结果有效率 | 未抛异常 **且** 结果不含错误关键词 | 更贴近"用户真的拿到了数据" |

明细会落盘到 `logs/eval_agent_report.json`，可逐条复查。

## 4. 扩充黄金集（重要）

`golden_set.json` 目前只有 15 + 10 条样例。**样本量小于 30 条时百分比会剧烈抖动**，
面试时经不起追问。建议扩到每类 ≥ 30 条：

```jsonc
// retrieval 段：期望命中的来源文件，可写多个（互为可接受答案）
{ "id": "R16", "query": "……", "expected_sources": ["故障排除.txt"] }

// agent 段：expected_tools 写期望调用的工具名，不需要工具就写 []
//           reference 必须来自真实知识库，不要臆造
{ "id": "A11", "query": "……", "expected_tools": ["rag_summarize"], "reference": "……" }
```

## 5. 实测结果（2026-09-28，本机 Docker）

入库规模：6 个文档 → 135 个片段（约 5.3 万字）。

| 指标 | 数值 | 口径 |
|---|---|---|
| Recall@1 | **60.0%** | top-1 命中期望来源文档 |
| Recall@3 | **80.0%** | 对齐线上 `rag_top_k=3` |
| Recall@5 | **86.7%** | 观察提升空间 |
| MRR@3 | 0.700 | 命中但排位靠后的惩罚 |
| 工具选择准确率 | 100% (10/10) | 实际工具集合 == 期望集合 |
| 工具调用成功率（无异常） | 100% (11/11) | 中间件未记 `!!` |
| 工具结果有效率 | 54.5% (6/11) | 见下方问题 4 |
| 问答准确率（LLM 裁判） | 50% (5/10) | 三轮实测在 30%~70% 间波动，见问题 5 |

> ⚠️ **两个关键结论**
> 1. **`Recall@3=80%` 是检索器单独跑出来的**。经由 Agent 端到端时命中率更低——因为模型会改写用户 query 再传给 `rag_summarize`，改写后可能检索不到（实测 A01 三轮里两轮未命中）。简历上若要写召回率，建议注明是"检索层口径"。
> 2. **"工具调用成功率 100%" 是个会骗人的指标**。它只反映"工具没抛异常"，而中间件会把异常兜底成 error ToolMessage，所以永远不抛。真实问题被"工具结果有效率 54.5%"暴露出来。两个数必须一起看。

## 6. 已发现的真实缺陷

| # | 问题 | 状态 |
|---|---|---|
| 1 | **知识库入库链路缺失**：`data/` 有 6 份文档，但代码里没有任何 TXT/PDF 切片入库实现，`data/chroma_db` 不存在，`rag_summarize` 永远返回"未找到" | ✅ 已补 `ingest_knowledge.py` |
| 2 | **`PROJECT_ROOT` 容器内越界**：`config.py` 上溯三级得到 `/`（代码在 `/app/app`），导致 `chroma_persist_dir=/data/chroma_db`、`UPLOAD_DIR=/data/uploads`、`LOG_DIR=/logs` 全部指向**未挂载**目录 → 向量库、上传文件、日志容器重建即丢 | ✅ 已修 `config.py`（改为探测式判定） |
| 3 | **`reset_collection()` 使其它进程句柄失效**：重建 collection 后，运行中的后端 worker 检索一律返回空，现象是"入库成功、脚本能查到、走 HTTP 却说没找到" | ✅ 入库脚本改为按 id 删除 |
| 4 | **`amap_around_search` 漏传必填参数 `location`**：模型只传 `keyword`，LangChain 参数校验失败 → 该工具 5 次调用全部无效（"结果有效率"只有 54.5% 的主因）。代码 docstring 里没说明 `location` 应取上一步 `amap_geocode` 的结果 | ⬜ 待修 |
| 5 | **错误消息污染上下文 → 整条 SSE 流中断**（问题 4 的连带后果，已定位到确切链路）：中间件把 LangChain 异常原文回灌给模型，而异常文本内嵌 Python 字典字面量 `{'keyword': '公园'}`（单引号）；模型下一轮模仿该格式生成 tool_call，DashScope 收到非法 JSON 直接 400 `InvalidParameter: The "function.arguments" parameter ... must be in JSON format` → 用户只拿到半截对话 | ⬜ 待修（P0） |
| 6 | **检索失败时模型仍自信作答**：`rag_summarize` 返回"未找到相关信息"后，模型用自己的知识补全答案，用户无法分辨。根因还有一层——**模型会改写 query**（把"日常保养"改写成"智扫通Pro X1 日常保养注意事项"，凭空加了型号），进一步压低端到端召回 | ⬜ 待修 |
| 7 | **把客户档案当成对话用户**：`system_prompt` 注入"客户信息：姓名=张三"，模型开口就称用户"张三先生"。客服场景里客户是**被服务对象**，不是对话者 | ⬜ 待修 |
| 8 | ~~语料乱码~~ **经核验不存在**：用 Python 逐文件检查，5 个 txt 的可疑字符数均为 **0**。先前看到的 `ã€` 是 Git Bash 终端输出中文时的显示编码问题，不是文件内容问题 | ✅ 已排除 |

> 问题 4~7 的完整根因分析与分步修改代码，见 [`docs/修复步骤-评测发现的缺陷.md`](../../docs/修复步骤-评测发现的缺陷.md)。

## 7. 已知问题

1. **语料乱码**：`维护保养.txt`、`扫拖一体机器人100问.txt` 存在部分 UTF-8 被二次编码的字符（如 `ã€`），会直接拉低召回表现。**建议先修复语料再测**，否则测出来的是数据质量问题，不是算法问题。
2. **PDF 与 TXT 重叠**：`扫地机器人100问.pdf` 与 `扫地机器人100问2.txt` 内容高度重复，黄金集里对相关问题同时接受两个来源。
3. **日志归属**：`[ToolCall]` 日志没有 conversation_id，脚本靠"提问前后行号区间"隔离。**评测时请串行执行**，不要与压测同时跑。
4. **裁判偏差**：LLM-as-judge 存在位置偏差与宽容倾向。建议抽 10% 人工复核，并在简历上注明是"LLM 裁判口径"。

## 8. 三个指标都低时的排查顺序

```
召回率低   → 语料乱码？chunk_size 太大？该知识点根本没入库？→ 考虑混合检索(BM25+向量)/查询改写
工具成功率低 → 缺 API Key？外部接口限流？参数 schema 不对？→ 用 POST /api/tools/{id}/test 直测区分"工具坏"还是"模型不会选"
问答准确率低 → 先看召回率：召回率正常但答案差 = 提示词/模型问题；召回率也低 = 检索问题
```
