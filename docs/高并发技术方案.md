# 高并发技术方案

> 本文是「智扫通智能客服 v2」应对高并发的系统性技术文档。
> 与 `deploy/locust/locustfile.py`、`docker-compose.yml`、`deploy/nginx/nginx.conf`、`backend/app/database.py` 配套阅读。
>
> 统一方法论：**先定位瓶颈，再动手调优**。每个小节都按
> 「问题 → 原理 → 具体配置/代码 → 验证方法」展开，不写空泛口号。
>
> 调优总顺序（务必遵守）：**CPU → 连接池 → DB 慢查询 → 外部 LLM 延迟**。

---

## 0. 全局认知：本项目的流量画像

- **读多写少**：聊天、列表查询是主力；写库主要是写消息、写记忆。
- **IO 密集为主**：一个聊天请求里要等「查 DB → 查向量库 → 调大模型流式输出 → 可能再调地图 API」，绝大多数时间在**等外部 IO**，而非算 CPU。
- **长连接存在**：SSE 聊天是秒级长连接，不是短请求，并发连接数会被放大。
- **重任务旁路**：CSV 入库、向量入库是重活，绝不能放在在线请求里同步做。

结论：本项目的高并发关键不是「把 CPU 跑满」，而是**在 IO 等待期间把事件循环让出去**，并把**有限的数据库连接**和**外部 API 配额**保护好。

## 1. 瓶颈定位方法论

### 问题
一慢就乱调参数，往往越调越糟。必须先知道瓶颈到底在 CPU、内存、IO、连接池、数据库还是外部 API。

### 原理
一条请求的耗时 = 等待各种资源的时间之和。哪段最长，瓶颈就在哪。分层打点：网关 `urt`（上游响应时间）→ 应用日志 → DB 慢查询 → 外部调用耗时。

### 具体怎么看（命令/工具）

| 资源 | 看什么 | 常用命令 |
|---|---|---|
| CPU | user 态是否打满、是否单核跑满 | `top` / `htop`；容器 `docker stats`；Windows 任务管理器 |
| 内存 | 是否吃到 swap、是否 OOM | `free -h`；`docker stats`（MEM USAGE） |
| 磁盘 IO | 是否 IO wait 高 | `iostat -x 1`；容器 `docker stats` |
| 网络/连接 | TIME_WAIT 是否堆积、连接数 | `ss -s`、`netstat -an \| findstr ESTABLISHED` |
| DB 连接池 | 活跃/空闲/等待数 | MySQL: `SHOW STATUS LIKE 'Threads%'; SHOW PROCESSLIST;` |
| DB 慢查询 | 是否有全表扫描 | 开启 `slow_query_log`，`EXPLAIN` 看执行计划 |
| Redis | 命中率、内存、阻塞 | `redis-cli info stats`、`redis-cli info memory` |
| Nginx 上游 | 哪段耗时 | 日志里 `$upstream_connect_time/$upstream_header_time/$upstream_response_time`（已在 nginx.conf 配置） |
| 外部 API | LLM/地图耗时 | 应用日志打点，对比后端 CPU 低但 RT 高 = 外部瓶颈 |

### 验证方法
1. 压测时**另开一个终端**持续观察 `docker stats` 与 `top`。
2. 把请求按接口拆分看 Locust 的 P95：只有 `/api/chat/stream` 慢 → 外部 LLM；列表接口也慢 → DB/连接池。
3. 经验判据：
   - 后端 CPU > 80% 且 QPS 上不去 → **计算瓶颈**。
   - CPU/DB 都闲，聊天 RT 高 → **外部 LLM/地图瓶颈**。
   - 日志出现 `QueuePool limit` → **连接池瓶颈**。

## 2. 全链路异步化

### 问题
FastAPI 虽是异步框架，但只要在 `async def` 里调用了**阻塞代码**（同步驱动、同步 SDK、CPU 密集计算），就会卡住整个事件循环，并发能力断崖式下跌。

### 原理
- 协程在 `await` 一个 IO 操作时会让出事件循环，去处理别的请求——这就是高并发的来源。
- Python 有 **GIL**：同一进程内同一时刻只有一个线程执行 Python 字节码。所以：
  - **IO 密集**（等网络/DB/LLM）→ 用 `async/await`，单进程可扛大量并发连接。
  - **CPU 密集**（大量计算）→ 异步没用，GIL 会把你串行化，应开**多进程**（uvicorn `--workers N`）或丢给 Celery。

### 具体配置/代码
- Web 层全用异步：路由写 `async def`，ORM 用异步 `aiomysql`（项目 `database.py` 已是 `create_async_engine`）。
- **阻塞式 LLM/同步 SDK 调用**必须丢到线程池，别阻塞事件循环：
  ```python
  from starlette.concurrency import run_in_threadpool

  # 若某个 LLM client 只有同步方法：
  result = await run_in_threadpool(sync_llm_client.call, prompt)
  ```
- uvicorn 多进程（compose 已配）：
  ```bash
  uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4
  ```
  worker 数经验值 ≈ `CPU 核数 × 2 + 1`；本项目 LLM 等待多，worker 可略高于核数。
- 不要在请求里做 CPU 重活（ pandas 大表计算、批量向量编码）→ 丢 Celery。

### 验证方法
- 压测时 `top` 观察：4 个 worker 进程是否都吃到了 CPU（说明多进程生效）。
- 对比实验：把某个阻塞调用临时去掉，看 QPS 是否大幅上升——若上升，说明它正在阻塞事件循环，需 `run_in_threadpool`。

## 3. MySQL 连接池调优

### 问题
每个请求都新建/销毁 TCP + MySQL 握手太贵；但开太多连接又会把 MySQL 打满（`Too many connections`）。需要一个池子复用连接。

### 原理
连接池预先建好一批连接复用。关键约束：
```
后端总连接数 ≈ worker 数 × (pool_size + max_overflow)
必须 < MySQL max_connections，并给监控/celery/预留连接留余量。
```

### 具体配置（本项目 `backend/app/database.py`）
```python
engine = create_async_engine(
    settings.async_database_url,
    pool_size=20,          # 常驻连接数（每个 worker 进程内）
    max_overflow=30,       # 峰值额外可建连接 → 单进程上限 50
    pool_recycle=3600,     # 连接最大存活秒数，必须 < MySQL wait_timeout(默认28800)
    pool_timeout=30,        # 拿不到连接时最多等 30s，超时报错
    pool_pre_ping=True,    # 取连接前先 ping，避免用到已被服务端断开的“死连接”
)
```
配套（`docker-compose.yml`）：MySQL `--max_connections=500`、`--innodb_buffer_pool_size=512M`。

**怎么算本项目上限**：4 worker × (20+30) = 200 连接 < 500，剩余给 celery(4) 和运维，安全。
> 注意：**盲目加 worker 会线性放大 MySQL 连接**。从 4 worker 加到 8 worker，连接需求就变成 400，逼近 500 上限。

### 各参数含义速查
| 参数 | 含义 | 典型值 | 调大的代价 |
|---|---|---|---|
| `pool_size` | 常驻空闲连接 | 10~30 | 占 MySQL 连接名额 |
| `max_overflow` | 峰值突增连接 | 10~50 | 峰值时瞬时压力 |
| `pool_recycle` | 连接回收秒 | 1800~3600 | 太短频繁重建，太长遇 `wait_timeout` 断连 |
| `pool_timeout` | 等连接超时 | 30 | 太短易误报错 |
| `pool_pre_ping` | 取前探活 | True | 多一次轻量 ping，强烈建议开 |

### 验证方法
- 观察连接数：
  ```sql
  SHOW STATUS LIKE 'Threads_connected';   -- 当前已用连接
  SHOW VARIABLES LIKE 'max_connections';
  ```
- 压测时看后端日志是否出现 `QueuePool limit of size ... overflow ... reached, connection timed out`——出现即池子不够或泄漏。
- 慢查询日志确认连接没被长事务占着不放（长事务会把连接占住不归还池子）。

## 4. Redis 缓存策略

### 问题
热点数据（客户列表、工具列表、会话状态）每次都查 MySQL 会拖慢 DB；限流计数、会话状态也需要一个低延迟共享存储。

### 原理
把「读多写少、容忍短暂不一致」的数据放进 Redis（内存，亚毫秒），回源时才查 DB。配套防三类经典缓存事故。

### 具体配置/代码
- 缓存热点数据：客户列表、工具列表、数据集列表查完写 Redis，设较短 TTL（如 30~60s），写库时失效。
- 会话/限流：用 Redis 做计数器（天然原子、多进程共享）。
- 缓存**穿透/击穿/雪崩**防护：
  - **穿透**（查不存在的 key 打到 DB）：对空结果也短缓存（如 30s 空对象），或布隆过滤器。
  - **击穿**（热点 key 失效瞬间海量请求回源）：热点 key 不过期 / 用互斥锁（`SETNX`）只放一个请求去回源。
  - **雪崩**（大量 key 同时过期）：TTL 加随机抖动，如 `TTL = 300 + random(0~60)`。
- 本项目 Redis 已配淘汰策略（compose）：`--maxmemory 256mb --maxmemory-policy allkeys-lru`（内存满时 LRU 淘汰，优先留热点）。

### 验证方法
```bash
redis-cli info stats          # keyspace_hits / keyspace_misses → 命中率应 > 90%
redis-cli info memory         # used_memory 是否逼近 256mb
redis-cli dbsize              # key 数量是否合理
```
命中率低 → TTL 太长/key 没设计好；内存满频繁淘汰 → 调大 `maxmemory` 或排查大 key。

## 5. 无状态水平扩展

### 问题
单台后端扛不住时，能不能简单地「再加一个后端实例」？前提是后端**不存任何会话状态**。

### 原理
- JWT 是**无状态**的：登录后把身份签名放进 token，后续请求带 token，后端只验签不查 session 存储（项目 `utils/security.py` 用 jose 签 HS256）。多实例拿到任意一个 token 都能验。
- 因此后端进程之间不需要共享 session，Nginx 把请求轮询到任意 worker 都能正确处理。
- **反例**：如果把登录态存在进程内存（`dict`/`flask-session` 内存版），用户第二次请求被轮到另一台就「掉登录」。本项目 session 全部走 JWT + Redis，不落进程内存。

### 具体配置
- Nginx upstream 加机器即可水平扩容（`deploy/nginx/nginx.conf`）：
  ```nginx
  upstream backend_servers {
      server backend:8000;
      server backend2:8000;   # 加第二台后端
      keepalive 32;           # 与后端保持长连接，避免反复三次握手
  }
  ```
- 所有实例用**同一个 `JWT_SECRET_KEY`**（否则互相验签失败）。
- 上传文件/向量库等有状态数据放共享卷或对象存储，别绑死单机本地磁盘。

### 验证方法
- 起两个 backend 容器，登录后连续刷新页面，无论 Nginx 轮到哪台都不 401。
- `docker stats` 看两台 CPU 是否被均匀打满（轮询生效）。

## 6. Nginx 配置要点

### 问题
Nginx 是统一入口，配错会成为瓶颈或把 SSE 弄成假流式。

### 原理
- upstream `keepalive`：Nginx 与后端复用 TCP 连接，省去每次握手。
- **SSE 必须关 `proxy_buffering`**：Nginx 默认会把后端响应先缓冲够一大块再发给客户端。SSE 是一条一条推消息的，缓冲一开，消息就被攒着，前端看起来就是「不流式、一次性蹦出来」。
- worker_connections 决定单进程并发连接上限。

### 具体配置（本项目 `deploy/nginx/nginx.conf` 已就绪）
```nginx
worker_processes auto;
events {
    worker_connections 4096;     # 单 worker 并发连接；SSE 长连接多要调大
    use epoll;
    multi_accept on;
}
http {
    client_max_body_size 50m;    # 允许上传大 CSV
    upstream backend_servers {
        server backend:8000;
        keepalive 32;            # 复用与后端的长连接
    }
    # SSE location 关键三行：
    location /api/chat/stream {
        proxy_buffering off;     # 必须关！否则不实时
        proxy_cache off;
        chunked_transfer_encoding on;
        proxy_read_timeout 300s; # 长聊天别被 60s 掐断
    }
}
```

### 验证方法
- 打开聊天页，应看到文字**逐字/逐段冒出**，而非等几秒整段出现。
- `nginx -t` 校验配置；压测时看 Nginx `worker_connections` 是否打满（日志 `worker_connections are not enough`）。
- 改完 `nginx -s reload`，不用重启容器。

## 7. 限流降级

### 问题
大模型按 token 计费且有 QPS 上限，恶意/突发流量可能把外部 API 打挂或产生巨额账单；DB 也需要保护。

### 原理
- **限流**：在入口按用户/IP 控制速率。Redis 令牌桶是经典算法——桶里固定容量的令牌，按固定速率补充，每个请求取一个令牌，取不到就拒绝。多进程共享计数必须放 Redis，不能放进程内存。
- **超时/熔断/退避**：外部依赖慢了要快速失败，不要让请求堆积；失败后指数退避重试。

### 具体配置/代码
令牌桶伪代码（Redis 用 Lua 保证原子）：
```python
# key = f"rate:{user_id}"
# rate = 每秒补 5 个令牌；capacity = 桶容量 20
lua_script = """
local key = KEYS[1]
local rate = tonumber(ARGV[1])      # 每秒补充数
local capacity = tonumber(ARGV[2])  # 桶容量
local now = tonumber(ARGV[3])
local tokens = tonumber(redis.call('GET', key) or capacity)
local last = tonumber(redis.call('HGET', key, 'ts') or now)
# 按时间差补充令牌，不超过容量
tokens = math.min(capacity, tokens + (now - last) * rate)
local allowed = 0
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('SET', key, tokens)
redis.call('EXPIRE', key, 60)
return allowed
"""
# allowed == 0 → 返回 429 Too Many Requests
```
- 框架层用 `slowapi`（已在 requirements）做声明式限流：
  ```python
  from slowapi import Limiter
  from slowapi.util import get_remote_address
  limiter = Limiter(key_func=get_remote_address)
  # @limiter.limit("10/second") 挂在路由上
  ```
- 给所有外部调用设**超时**（httpx `timeout=10`），不要无限等；LLM 调用失败时返回友好降级文案，而不是 500。

### 验证方法
- 把限流阈值临时调小（如 1/s），用 Locust 快速请求，确认返回 429 且后端不被打挂。
- 模拟 LLM 慢响应，确认请求在超时时间内被切断，Nginx/后端连接不堆积。

## 8. Celery 削峰填谷

### 问题
CSV 导入几万行、批量文本向量化是 CPU+IO 重活，同步做会把在线请求卡死（HTTP 超时、占着 DB 连接不放）。

### 原理
把重任务扔进消息队列（Redis broker），立即返回一个任务 ID；在线请求立刻释放去处理别人；Celery worker 在后台慢慢消费；前端轮询任务进度。这样「峰」被削平，DB/向量库压力由 worker 平滑消化。

### 具体配置
- broker/backend（`.env`）：
  ```
  CELERY_BROKER_URL=redis://127.0.0.1:6379/1
  CELERY_RESULT_BACKEND=redis://127.0.0.1:6379/2
  ```
- 启动（compose 已配）：`celery -A app.tasks.celery_app.celery worker --concurrency=4`
- 业务流程：
  1. 上传 CSV → 落 `data/uploads`，往 `async_tasks` 表写一条 `pending` 记录，丢 Celery。
  2. worker 解析 CSV、建表、批量入库、写进度（`async_tasks.progress`）。
  3. 前端轮询 `GET /api/datasets/{id}` 看状态 `processing/completed/failed`。

### 验证方法
- 上传一个大 CSV，接口应秒回（不阻塞），聊天接口依然飞快。
- `docker-compose logs celery_worker` 看任务消费进度；`async_tasks` 表里 progress 从 0 走到 100。

## 9. 数据库优化

### 问题
连接池调好了，但单条 SQL 慢照样拖垮一切。

### 原理
高并发下 DB 是最贵的资源：每条慢 SQL 都会长时间占着一个连接不放，放大成连接池耗尽。

### 具体配置/原则
- **索引设计**：给 `where`/`join`/`order by` 字段建索引（本项目已建 `idx_phone`、`idx_customer`、`idx_status` 等，见 `sql/init.sql`）；避免过度索引拖慢写入。
- **慢查询分析**：
  ```sql
  -- 开慢日志后，用 EXPLAIN 看执行计划
  EXPLAIN SELECT * FROM customers WHERE phone = '13800138001';
  -- 重点看 type 列：ALL = 全表扫描(坏)，ref/eq_ref = 走索引(好)
  -- 看 rows 列：扫描行数是否过大；Extra 不要出现 Using filesort / Using temporary
  ```
- **读写分离（概念）**：主库写、从库读，把列表查询这种读压力分流。数据量大了再上。
- **分库分表（概念）**：单表千万级再考虑；本项目客户量远没到，过早优化是负资产。

### 验证方法
- 开 `slow_query_log`，把超过 1s 的 SQL 抓出来逐个 `EXPLAIN`。
- 压测时 `SHOW PROCESSLIST` 看有没有长时间运行的查询占着连接。

## 10. 压测与容量规划

### 问题
「到底能扛多少并发？」不能拍脑袋，要压出来。

### 原理
**利特尔法则**：`并发数 N ≈ 目标 QPS × 单请求平均耗时 T(秒)`。
找拐点：逐步加压，直到 P95 延迟陡增或错误率 >1%，那个点就是容量上限。

### 具体步骤（脚本在 `deploy/locust/locustfile.py`）
```bash
cd deploy/locust
pip install -r requirements.txt
locust -f locustfile.py --host=http://localhost:8000 \
    --users=100 --spawn-rate=10 --run-time=5m --headless --html=report.html
```
举例：聊天接口平均 3s、目标 50 QPS → 需要约 `50 × 3 = 150` 并发连接；列表接口 0.1s、200 QPS → 约 20 并发。
然后按 50 → 100 → 200 → 300 用户阶梯加压，记录每档的 QPS / P95 / 错误率。

### 调优顺序 Checklist（压测时照此排查）
1. ☐ CPU 是否打满？是 → 加 worker / 重任务下沉 Celery。
2. ☐ 日志是否 `QueuePool timeout`？是 → 调连接池（注意 MySQL 上限）。
3. ☐ 是否有慢 SQL？是 → 加索引 / 优化。
4. ☐ CPU/DB 都闲但聊天慢？是 → 外部 LLM/地图，做缓存/超时/降级。
5. ☐ 连接数是否逼近 MySQL `max_connections`？是 → 扩 DB 或减 worker。

### 验证方法
- 看生成的 `report.html`：每个接口 P50/P95/P99、失败率、RPS。
- 压测同时采集 `docker stats`、MySQL `Threads_connected`、Redis 命中率，三者对照定位。

## 11. Agent 并发安全

### 问题
如果把一个**带状态的 agent 实例**做成全局单例，被多个并发请求共享，会发生「A 客户的问题被塞进了 B 的对话历史」这种串话事故。

### 原理
LangChain/LangGraph 的 agent 运行时常常携带可变状态（对话历史、中间变量、当前工具输出）。请求是并发交错的，若共享同一个可变实例，后一个请求的 `await` 间隙会被另一个请求写入，状态互相污染。

### 具体配置/原则
- **每次请求轻量构建 agent**：在请求处理函数里根据当前用户/会话**新建** agent run（传入该会话独立的 memory/状态），用完即弃。构建成本小（只是拼工具和系统提示），不要为此做全局单例。
- **重对象做成无状态单例**：数据库引擎、连接池、配置、只读的大模型 client、Chroma 客户端这类**无状态、线程安全、构造昂贵**的对象，才适合全局单例复用（本项目 `engine`、`settings` 就是模块级单例）。
- 一句话区分：**有会话状态的 = 每请求新建；无状态且贵的 = 全局单例**。

### 验证方法
- 并发压测时用两个不同 `customer_id` 同时聊天，检查各自的回答/记忆没有串到对方（日志里打印 customer_id 与会话内容核对）。
- 代码 review：确认没有把 `chain`/`agent` 的可变 history 挂在全局变量上跨请求复用。

## 附：一页纸总结

| 维度 | 本项目做法 |
|---|---|
| 异步 | FastAPI async/await，阻塞调用 `run_in_threadpool`，CPU 重活走 Celery |
| 连接池 | pool_size 20 + max_overflow 30，pre_ping，4 worker 共占 ≤200 < MySQL 500 |
| Redis | 热点缓存 + 限流计数 + LRU 淘汰 256mb，防穿透/击穿/雪崩 |
| 水平扩展 | JWT 无状态，Nginx upstream 加机器，session 不落内存 |
| Nginx | keepalive、SSE 关 proxy_buffering、worker_connections 4096、body 50m |
| 限流降级 | Redis 令牌桶 + slowapi + 外部调用超时熔断 |
| 削峰 | Celery 跑 CSV 入库/向量化，前端轮询进度 |
| DB | 索引 + 慢查询 EXPLAIN，必要时读写分离 |
| Agent 安全 | 有状态 agent 每请求新建，无状态重对象单例 |

调优永远是：**先压测定位瓶颈，再对症下药，一次只改一类参数并回归验证**。
