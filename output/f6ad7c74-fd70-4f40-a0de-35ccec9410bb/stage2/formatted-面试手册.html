〇、先记住这套「主线故事」

面试官只有 30 秒耐心听你介绍项目。你开口的第一分钟决定他后面往哪问。

30 秒版（自我介绍里带一句）

  "我独立做过一个面向扫地机器人售后的智能客服系统，用 FastAPI + LangGraph 做后端，核心是把 RAG 检索、工具调用、Text2SQL 三条能力统一到一个 ReAct Agent 里，支持流式对话。工程上做了全异步改造和容器化部署，能一键拉起。"

3 分钟版（他让你详细讲时用）

S（背景）：原型版是个"一问一答的聊天框"——只能回答写死的问题，覆盖窄，而且客服真正需要的三件事它都做不到：查知识库、查客户档案、调外部服务（地图/天气）。

T（任务）：我要把它改成一个能"自己判断该查什么"的 Agent 系统。

A（行动）：做了四件事——

  1. 用 LangGraph 的 ReAct 循环替代写死的问答规则，让模型自己决定"思考→选工具→看结果→再回答"；
  2. 建 RAG 知识库，把故障/保养文档切片向量化，回答前先检索，压制幻觉；
  3. 让 Agent 能查 MySQL 里的客户档案，并接高德/百度的地理编码、天气、周边 POI；
  4. 加 长期记忆，自动抽取客户偏好，下次会话召回。

同时做了工程化：全异步 IO、连接池、Celery 削峰、Nginx 负载均衡 + SSE 优化、Docker Compose 一键部署。

R（结果）：跑通了完整链路，并用自建的评测集量化了效果——检索层 Recall@3 达 80%、工具选择准确率 100%、端到端问答准确率约 50%~70%（样本 10 条，波动大，正在扩样本）。

  ⚠️ 诚实提示：数字要经得起追问。上面"50%~70%"是真实实测区间，面试时主动说明"样本量小、正在扩到 30 条以上"，比吹成 89% 被问穿要安全得多。

一、技术选型篇

本篇 4 问，全部围绕「为什么这么选、代价是什么」：后端框架、存储组合、向量库、前端技术栈。面试官问选型时想确认的不是你选了哪个，而是你说得出代价。

Q1：为什么后端选 FastAPI，不用 Django 或 Flask？

  面试官想确认：你是"跟着教程选的"还是"想过为什么"。

答（按结论→理由→代价说）：

选 FastAPI 是三个原因叠加的：

  1. 原生异步。这个项目的核心链路是"一个请求里要等四次外部 IO"——查 DB → 查向量库 → 调大模型流式输出 → 可能再调地图 API。全程几乎不耗 CPU，全是在等网络。Flask 是 WSGI 同步模型，一个 worker 等 IO 时就阻塞了；FastAPI 是 ASGI，await 期间会把事件循环让出去处理别的请求。这个项目并发能力的天花板主要在这里。
  2. SSE 流式响应好写。FastAPI 直接返回 StreamingResponse 包一个 async generator 就行。
  3. Pydantic 做请求/响应校验。这个项目里工具参数也是 Pydantic 动态建的模型，全栈一套类型系统。

代价也说清楚：Django 自带的 ORM、Admin、权限体系我全都要自己搭；生态上异步中间件比 Django 少。但如果重来我还是选 FastAPI，因为 IO 密集 + 流式这两个特征它最合适。

追问：那 Django 的 ORM 比 SQLAlchemy 好用，你不觉得可惜吗？

  会。Django ORM 的迁移和 Admin 确实省事。但 Django ORM 的异步支持是后来补的，底层还是 sync_to_async 包一层，跟 SQLAlchemy 2.0 原生 async 不是一个量级。我这个项目 DB 等待时间占比很高，所以异步纯度比开发效率更重要。

Q2：为什么用 MySQL + Redis 两个存储？不能只用 MySQL 吗？

答：两者职责不同，不能互相替代：

  • MySQL 是事实源：用户、客户、会话、消息、长期记忆、数据集元数据，都要持久化、要事务。
  • Redis 干三件事：① 接口缓存和限流计数器；② Celery 的 broker 和 result backend；③ 会话级临时数据。这三件事要么是高频读写（MySQL 扛不住），要么是本来就该过期的（MySQL 存了要清理）。

追问：那长期记忆的向量为什么存 MySQL 不存 Redis 或向量库？

  这是我权衡过的一个点。单客户记忆量是有界的——几十到几百条，不是百万级。我把 embedding 存 MySQL 的 JSON 字段，召回时把该客户记忆全量取出来，在 Python 端算余弦。好处是少一套基础设施，MVP 阶段最稳。代价是 O(n) 全量扫描，但 n 有界所以可接受。如果记忆量涨到十万级以上，我会迁到 pgvector 或 Milvus，按 customer_id 做分区。代码上我已经留了口子——召回只有一个入口 retrieve_relevant()，换底层只改这一处。

Q3：向量库为什么选 Chroma，不选 Milvus / FAISS / pgvector？

答：按"数据规模 → 部署复杂度"排的：

  • 我的知识库是几万字级别、几百个 chunk。这个量级下，Chroma 和 Milvus 的检索性能差异在噪声范围内。
  • Chroma 是嵌入式的，跟应用同进程，pip install 就能用，落盘就是本地文件；Milvus 要单独部署一套集群（etcd + MinIO + 多个服务），对我这个规模是过度设计。
  • FAISS 只是索引库，不带持久化和 metadata 过滤，我还要自己管 id 映射。

追问：那什么时候你会换掉 Chroma？

  三个信号：① 向量数到百万级，单机内存扛不住；② 需要多租户隔离和细粒度权限；③ 需要水平扩展（多副本读写分离）。Chroma 是单机嵌入式，这三条它都做不到。真到那时候我会换 Milvus 或 pgvector——特别是 pgvector，如果我的业务数据本来就在 PG 里，用它能把"关系数据 + 向量"放在一个事务里，运维成本最低。

Q4：前端为什么用 Vue 3？为什么不用 Streamlit 那种现成的？

答：原型版确实用了 Streamlit，改 v2 时换成了 Vue 3 + Vite。

原因是 Streamlit 有三个硬伤：

  1. 它是一体的——页面和 Python 逻辑绑死，没法做前后端分离，也接不了独立的鉴权体系；
  2. 流式输出控制粒度粗，做不到我想要的那种"逐 token 打字机 + 工具调用过程可见"；
  3. 它不适合做后台管理系统——我这个项目还有客户管理、工具管理、数据集管理、记忆管理四个页面。

换 Vue 3 的收益：SPA 路由、Pinia 管状态、Element Plus 直接出后台界面，而且前后端分离后，后端 API 可以独立给别的端复用。

追问：那 Vue 和 React 你怎么选的？

  说实话这个项目我选 Vue 更多是因为开发速度快——Element Plus 的后台组件比 Ant Design 更开箱即用，单文件组件写起来心智负担小。如果团队已经在用 React，我会跟着团队走，这个层面没有技术优劣，只有协作成本。

二、后端架构篇

本篇 4 问，覆盖分层设计、SSE 的 session 生命周期、连接池参数、JWT 鉴权。其中第 2 问是高频深挖点，通常会被连续追问三层以上。

Q5：讲一下你的后端分层，为什么要这么分？

答：四层，单向依赖：

api/          HTTP 层：路由、参数校验、鉴权、响应包装
  ↓
services/     业务层：编排逻辑（chat_service / text2sql_service / memory_service）
  ↓
repositories/ 数据访问层：所有 SQL 都在这层
  ↓
models/       ORM 模型：表结构映射

为什么这么分——不是我为了好看，是被两个具体问题逼的：

  1. 测试和替换。业务逻辑（比如"先召回记忆再拼 prompt"）如果和 SQL 混在一起，我想换个存储就得改业务代码。分层后 services 只依赖 repositories 的接口。
  2. 复用。同一个查询在 HTTP 接口和 Agent 工具里都要用。比如查客户档案：HTTP 有个 /api/customers，Agent 里有个 get_customer_info 工具，两个入口共用 CustomerRepository，不会出现两份 SQL。

追问：那你说分层，实际有破例吗？

  有，而且是故意的。api/chat.py 里直接 from app.database import AsyncSessionLocal 手开了 session，没走 get_db 依赖注入。原因在下面 SSE 那题会讲——这是流式响应的特殊要求，不是分层没做干净。

Q6：SSE 流式接口的 session 生命周期，你是怎么处理的？（高频深挖点）

答：这是个很容易踩的坑，我讲下我的做法。

问题：FastAPI 的 Depends(get_db) 依赖，它的 finally 是在响应函数返回后执行的。但 SSE 是长连接——响应函数返回时，流才刚开始吐。如果走依赖注入，session 会在第一个 chunk 吐出去之前就被 close，后面全是报错。

我的做法：在路由函数内部手动持有 session，把整个流的生成器写在这个上下文里：

async def event_generator():
    async with AsyncSessionLocal() as db:      # session 生命周期 = 整个流
        try:
            async for chunk in ChatService.stream_chat(db=db, ...):
                yield f"data: {json.dumps({'content': chunk})}\n\n"
            yield "data: [DONE]\n\n"
        except Exception as e:
            err = json.dumps({"error": _friendly_error(e)})
            yield f"data: {err}\n\n"
            yield "data: [DONE]\n\n"

async with 保证流结束（或异常）后 session 一定被释放，不会泄漏连接。

追问：那异步生成器里如果中途抛异常，session 会泄漏吗？

  不会。async with 的 __aexit__ 在异常路径上也会执行。但有个更隐蔽的：记忆抽取是后台任务，我用 asyncio.create_task 丢到后台跑，它不能复用请求的 session——请求的 session 在流结束后就被关了。所以后台任务必须自己开一个独立 session。

追问（杀手锏）：asyncio.create_task 有什么坑？

  有，我踩过。asyncio.create_task() 的返回值如果没有被任何变量持有，Python 的垃圾回收可能在任务跑完之前就把 Task 对象回收掉，导致任务被静默取消——不报错、没日志，就是记忆没写进去。我的修法是维护一个模块级的 set 把任务"按住"，并用 add_done_callback 在完成后移除，避免集合无限增长。

Q7：连接池参数怎么定的？

答：pool_size=20, max_overflow=30, pool_recycle=3600, pool_timeout=30, pool_pre_ping=True。

  • pool_size=20 + max_overflow=30 = 单 worker 峰值 50 个连接。我起了 2 个 worker，峰值 100。MySQL 那边 max_connections 我设了 500，留了足够余量。
  • pool_recycle=3600：MySQL 默认 wait_timeout 是 28800 秒（8 小时），但中间可能有防火墙/NAT 静默断连。设成 3600 秒主动回收，比等到用的时候才发现连接死了要好。
  • pool_pre_ping=True 是最关键的一个：取连接前先 ping 一下，失效就换一个。没有它，容器重启、DB 重启后会出现一批"连接存在但已断开"的报错，而且报错位置在业务代码里，很难定位。

追问：连接池设 20 是不是拍脑袋的？

  是经验值起步，但我知道该看什么指标去调：SHOW STATUS LIKE 'Threads_connected'看实际并发连接数，以及日志里有没有 QueuePool limit ... overflow 的告警。后者出现说明池子不够。真要调优我会先压测拿到 P95，再看是池子不够还是 DB 慢查询。

Q8：JWT 鉴权怎么做的？为什么无状态很重要？

答：登录 POST /api/auth/login 用 form 表单收 username/password，校验通过后用 python-jose 签发 JWT（HS256），前端存在 localStorage，后续请求带 Authorization: Bearer <token>。

为什么强调无状态：因为这个系统要能水平扩展。如果 session 存在单机内存里，我加一台后端机器，用户请求被 Nginx 轮询到另一台就掉登录了。JWT 把状态放在 token 里，任何一台机器都能独立验签，加机器就是加机器，不需要 session 共享。

追问：那 JWT 有什么缺点？你怎么处理？

  最大的问题是无法主动失效——token 签发后到期之前一直有效，用户登出、改密码、被封号都拦不住。

  我的应对：① 有效期设 1440 分钟（1 天），不设太长；② 生产环境所有实例必须用同一个 JWT_SECRET_KEY，否则验签失败；③ 如果真需要主动吊销，就得引入 Redis 黑名单——把未过期但已登出的 token 存进 Redis 设 TTL，每次校验多查一次 Redis。代价是从"纯无状态"变成"半有状态"，但换来了可控性。这个取舍我清楚，只是当前阶段没做。

三、数据库篇

本篇 3 问：表设计、索引依据、慢查询排查路径。回答时把「表结构 → 索引 → 执行计划」串成一条线，比单点罗列更有说服力。

Q9：讲一下你的表设计。

答：8 张表，分四组：

组表说明
账号users后台操作员，bcrypt 存密码哈希
业务customers客户档案，phone 唯一
会话conversations / messages会话与消息，级联删除
AIlong_term_memories / custom_tools记忆（含 embedding）、工具定义
数据datasets / async_tasks数据集元数据、异步任务进度

几个设计决策：

  1. messages 和 conversations 用外键 + ON DELETE CASCADE。删会话时消息自动清掉，不会留孤儿数据。这个在 ConversationRepository.delete 里也做了显式处理，双保险。
  2. custom_tools.parameters_schema 用 JSON 字段。因为每个工具的参数结构都不一样，用一个 JSON 字段描述，代码里动态建 Pydantic 模型。这是"配置驱动"的关键——加工具不用改表结构。
  3. long_term_memories.embedding 也用 JSON。理由在选型篇讲过，量有界所以能接受。

追问：JSON 字段存 embedding，查询性能怎么办？

  不查。embedding 这一列从来不参与 SQL 的 WHERE 和 ORDER BY——它只是"顺路存在这里"的数据，取出来之后在 Python 端算余弦。所以 JSON 字段的"不能建索引"这个缺点对我没影响。真正参与查询的是 customer_id，那个我建了索引。

Q10：索引怎么建的？为什么建这些？

答：原则是"建在被高频过滤和排序的列上"。

  • messages.idx_conversation (conversation_id)：查历史消息必须按会话过滤，最高频。
  • messages.idx_created (created_at)：消息要按时间正序/倒序取，短期记忆窗口是"取最近 N 条"。
  • conversations.idx_customer (customer_id)：按客户列会话。
  • customers.idx_city / idx_phone：按城市筛客户（"深圳有哪些金卡用户"），手机号是唯一键本身有索引。
  • custom_tools.idx_enabled (is_enabled)：启动时 WHERE is_enabled=1 加载工具。
  • async_tasks.idx_task_id：前端轮询任务进度，按 task_id 查。

追问：is_enabled 这种区分度极低的列建索引有意义吗？

  好问题。单看区分度确实低（大部分工具都是启用的），如果表有几十万行，这个索引基本不会被优化器选中。但我的 custom_tools 表只有个位数到几十行，全表扫描和走索引没区别，建它是为了语义明确，以及万一工具数量涨起来能兜住。说实话这条索引的收益接近于零，属于"顺手建的"。

  💡 这个回答的加分点在于：主动承认某条索引收益不大，比硬编一个理由要可信。

Q11：如果现在数据库慢查询变多，你怎么排查？

答：按这个顺序，不跳步：

  1. 先看是不是索引问题。开 slow_query_log，把慢 SQL 捞出来，逐条 EXPLAIN，看 type 是不是 ALL（全表扫描）、rows 扫了多少行。
  2. 再看是不是 SQL 写法问题。典型的有：LIKE '%关键词%' 前置通配符用不了索引；在索引列上做函数运算；SELECT * 把大字段（比如我的 embedding JSON）也捞出来。
  3. 然后看连接池。日志里有没有 QueuePool limit 告警。如果有，是池子不够，不是 SQL 慢。
  4. 最后看数据量。如果是单表几百万行了，考虑归档冷数据或者分表。

追问：那你知道这个项目里最可能出慢查询的是哪条吗？

  知道。retrieve_relevant 里 MemoryRepository.get_by_customer()——它会把某个客户的全部记忆连同 embedding 一起捞出来，然后在 Python 端算余弦。现在是几十条所以没事，如果某个客户积累到几千条记忆，这一条会立刻变成瓶颈。优化路径我在代码注释里写了：MySQL 8.0.32+ 的 VECTOR 类型可以把余弦距离下推到 SQL，再往上就是迁向量库做 ANN 检索。

四、AI Agent 篇（重点，面试官最关心）

本篇 8 问，是整份材料的重心：ReAct 原理、可观测性、工具注册与中间件、实例生命周期、流式输出、短期与长期记忆。建议把「工具结果有效率只有 54.5%」当作主动抛出的钩子。

Q12：什么是 ReAct？你为什么用 LangGraph 实现？

答：ReAct = Reasoning + Acting，让模型交替做"推理"和"行动"：思考该做什么 → 调工具 → 看工具结果 → 再思考 → 直到能回答。

传统做法是把问答规则写死：命中关键词 A 就查表 A，命中 B 就查表 B。问题是客服场景的问题是开放的自然语言，规则永远覆盖不全。

ReAct 的价值是把"选哪个工具"这个决策交给模型——我只要把工具描述写好，模型自己判断"这个问题该查知识库还是查天气"。

为什么用 LangGraph：LangGraph 把 Agent 的执行建模成状态图，每个节点（模型调用、工具执行）之间有明确的状态流转。相比早期 LangChain 的 initialize_agent（黑盒的 AgentExecutor），LangGraph 让我能在节点级别插入中间件、过滤流式输出——这点后面会讲到，是我踩坑最多的地方。

Q13：你怎么保证 Agent 执行过程是可观测的？（项目亮点，主动讲）

答：这是我做完最满意的一块。我用 LangChain 1.x 的中间件机制（切面）做了两个钩子：

  1. wrap_tool_call：包裹每一次工具调用，记录工具名、入参、返回值、耗时，并且捕获异常兜底——工具抛异常时返回一条 error ToolMessage，而不是让整个 Agent 循环崩掉。
  2. before_model：每次调模型前打印当前消息队列长度，用来发现"上下文无限堆积"这类问题。

为什么用中间件而不是在业务代码里打日志：工具是动态从数据库加载的，我不可能在每个工具函数里都手写一遍日志。中间件是"一次编写、包裹所有工具"，而且不改 Agent 本身的代码。

追问（关键）：那你怎么用这些日志量化效果？

  我把日志变成了评测数据源。日志格式是固定三行：[ToolCall] -> {工具名} args=... / [ToolCall] <- {工具名} result=... / [ToolCall] !! {工具名} 执行异常。我的评测脚本会记录提问前后的日志行号，只解析这个区间内的新增行，就能还原出"这一次提问到底调了哪些工具、成功了几次"。

追问（杀手锏，这里要讲透）：那你的"工具调用成功率"是多少？

  一开始我统计出来是 100%，看起来很好。但我不信，因为这个数太好了。我去查原因，发现一个很典型的陷阱：

  中间件把工具异常兜底成了 error ToolMessage，然后正常返回了。所以在日志里记的是 <-（成功返回）而不是 !!（抛异常）。结果就是——不管工具实际坏成什么样，这个指标永远是 100%。

  于是我补了一个更真实的指标：工具结果有效率——检查返回内容里有没有Error invoking tool、API调用失败、未找到相关信息 这类"没拿到数据"的标记。补上之后，真实数字是 54.5%，问题一下就暴露出来了。

  💡 这个回答的价值：体现你不盲信指标、会去验证数据合理性。面试官会记住"这个人说工具成功率 100% 但自己去质疑了"。

Q14：接着说，54.5% 的问题出在哪？（顺着往下讲，这是真实故事）

答：我定位到是 amap_around_search（高德周边搜索）这个工具，5 次调用全部失败。

日志里写得很清楚：模型调用时只传了 keyword，没传必填的 location（中心点经纬度）。

深挖下去有两层原因：

第一层，工具描述没说清楚 location 从哪来。这个工具的正确用法是：先调 amap_geocode 把地名转成经纬度，再拿这个经纬度调周边搜索。但我的工具描述里只写了"中心经纬度，格式 lng,lat"，没说"这个值必须来自上一步 geocode 的结果"，模型就不知道该怎么填，干脆不填。

第二层，也是更隐蔽的——错误消息把整条流搞崩了。参数校验失败后，LangChain 返回的错误文本长这样：

Error invoking tool 'amap_around_search' with kwargs {'keyword': '公园'} with error:
 location: Field required

注意 {'keyword': '公园'} 这坨东西——它是 Python 字典字面量，用的是单引号。这条消息进入对话历史后，模型下一轮生成工具调用参数时模仿了这个格式，生成了非法的 JSON。DashScope 收到后直接返回 400：

InvalidParameter: The "function.arguments" parameter of the code model must be in JSON format.

然后 astream 抛异常，SSE 生成器退出——用户拿到的是半截对话。

我的修法：中间件回灌给模型的错误消息，先把花括号片段剔除掉（re.sub(r"\{[^{}]*\}", "…", str(e))），原始异常只进日志不进上下文。同时补强工具描述，明确写出"location 必须取 amap_geocode 的返回结果"。

  💡 怎么讲这个故事：不要一上来就说"我改了一行正则"。要讲"我先看到现象 → 我怀疑 → 我挖到两层原因 → 一层是提示词、一层是错误处理污染上下文"。这个思考链路才是面试官想听的。

Q15：工具是怎么注册的？为什么做成动态的？

答：工具存在数据库 custom_tools 表里，启动时加载，支持运行期热更新（reload()）。

为什么不用写死的工具列表：如果工具写死在代码里，加一个工具就要改代码、重新构建镜像、重启服务。做成配置驱动后，加工具 = 插一条数据库记录，reload() 一下就能用。

支持四种类型：builtin（代码内置）、map_amap / map_baidu（地图类）、python_func（数据库里存 Python 代码片段，在受限命名空间 exec）、http_api（包装成 HTTP 调用）。

追问：python_func 允许在数据库里存任意 Python 代码，这不是很危险吗？

  非常危险，而且我在代码注释里就写明了这一点。我做了两层缓解：① exec 的全局命名空间只注入一个白名单内置函数表，剔除了 os / sys / subprocess / open / __import__，所以拿不到文件和网络能力；② 只有管理员能写 custom_tools 记录。

  但我必须说清楚：这不是真正的沙箱。 Python 的 exec 沙箱在语言层面就防不住（比如通过 ().__class__.__bases__[0].__subclasses__() 这种反射链绕出去）。生产环境我的建议是直接关掉 python_func 类型，只允许 http_api——真需要自定义逻辑就走 HTTP 服务，用网络边界隔离，比在进程内 exec 安全得多。

  💡 主动说出"我这块做得不够安全、生产该怎么改"，比被问出来强得多。

Q16：中间件有个坑你提到过，具体是什么？

答：LangChain 1.x 的中间件钩子签名有硬性要求，写错不会在构建时报错，只在执行时报错——这是最难查的一类问题。两个具体的：

  1. before_model 钩子必须接收两个参数 (state, runtime)。写成 (state) 时，create_agent() 构建阶段不报错，等到真聊天时才抛TypeError: takes 1 positional argument but 2 were given。
  2. wrap_tool_call 钩子里，工具信息在 request.tool_call 这个 dict 里（name / args / id），不是 request.tool_name。用老写法取不到值，日志里工具名全是 <unknown>，但不报错。

追问：那你怎么保证不会再踩这种坑？

  我在 Dockerfile 里加了构建期自检——docker build 阶段就跑一段脚本，验证 create_agent 能不能导入、中间件 API 能不能导入。如果依赖装错了版本，构建直接失败，而不是等容器跑起来才发现。这个改动很值：之前有次把 langchain 装成了 0.3.x，create_agent 不存在，但镜像居然构建成功了，容器起来后一直 unhealthy，查了很久。

Q17：你的 Agent 是每请求一个实例还是单例？为什么？

答：每请求一个新 SmartAgent 实例，但模型是全局单例。

  • SmartAgent 每次请求 build() 一个新的，因为它要携带本次请求的状态（客户 ID、会话 ID、工具列表、最近上下文）。它不持有跨请求的可变状态，所以用完即弃是安全的。
  • 但大模型对象和 embedding 对象是模块级单例（factory.py）。因为它们底层维护着到 DashScope 的连接池，每个请求都 new 一个会反复建连，既慢又费资源。

追问：那多进程 worker 之间呢？单例还成立吗？

  不成立。模块级单例是进程内的。我起了 2 个 worker，那就是 2 份模型对象。这没问题，只是"单例"的范围要说清楚是进程级不是全局级。如果哪天模型对象初始化很贵，我会考虑换成 --workers 1 + 内部线程池，或者把模型调用抽成独立的推理服务。

Q18：流式输出你踩过什么坑？（必问）

答：踩过一个很典型的，stream_mode 用错了。

LangGraph 的 astream 有两个模式：

  • stream_mode="values"：每跑完一个图节点返回一次全量状态。问题是——要等模型把整段话生成完才返回一次，所以分片数只有 1~3 个，前端看到的不是打字机，是"憋半天一次性蹦出一大段"。更麻烦的是这个全量状态里包含用户的提问和工具返回结果，做 diff 时容易把用户的问题、知识库原文混进回答里。
  • stream_mode="messages"：模型每生成一个 token 就返回一次 (增量, 元数据)。这才是打字机的来源。

还有一个细节：切到 messages 模式后，我发现答案会重复。原因是我的 rag_summarize 工具内部自己又调了一次大模型，那次调用的输出也被当成流式事件推给用户了。我的解法是用 metadata["langgraph_node"] == "model" 做过滤，只保留主模型节点的输出。

追问：那前端怎么配合？

  前端用 fetch + ReadableStream 手动解析，不能用 EventSource。因为 EventSource 不支持自定义请求头，带不了 Authorization: Bearer。解析时有两个细节：① 用 TextDecoder 的 {stream: true} 模式，因为一个中文字符的 UTF-8 字节可能被拆到两批网络包里；② 用一个 buffer 攒数据，按 \n\n 切事件，最后一段可能是半拉子事件，要留着等下一批。

Q19：Agent 的短期记忆和长期记忆怎么做的？

答：分开设计，因为生命周期完全不同：

  • 短期：取当前会话最近 N 轮（memory_recent_window=10）消息，直接拼进 prompt。SQL 层按 created_at desc 取 N 条再反序还原时间线。
  • 长期：存 MySQL，每条记忆带 embedding 和 importance。每轮对话结束后后台异步用 LLM 抽取"事实"和"偏好"（严格约束只输出 JSON），生成 embedding 落库。下次对话时按 query 召回，打分公式是 余弦相似度 × importance。

追问：为什么打分要乘 importance，不直接用相似度？

  因为"相关"和"重要"是两件事。举个例子：客户说过"我对噪音特别敏感"（重要偏好）和"今天下午三点打过电话"（不重要事实），如果 query 是"这个客户有什么特点"，后者的字面相似度可能还更高。乘上 importance 相当于给重要记忆加权，让"客户画像类"的记忆更容易被召回。

追问：为什么不用 LangGraph 自带的 Store？

  我专门查过这个。LangGraph 的 BaseStore 确实支持跨 thread 存记忆，但它的语义是"键值 + 可选向量"，而我要的是"客户级事实/偏好画像 + 重要性加权召回"——是两回事。用 Store 我还得自己实现画像的抽取和加权逻辑，那不如直接用 MySQL 控制得更细。另外 Checkpointer 和 Store 容易混淆：Checkpointer 管的是单次运行的线程内状态（断点续跑、恢复工具调用栈），不是跨会话的客户画像。这个边界我是在设计阶段就想清楚的。

五、RAG 与评测篇

本篇 5 问：RAG 全链路、评测方法、LLM 裁判可信度、适用边界、RAG 与 Text2SQL 的分流。这里的数字（Recall@3 80%）是全篇最容易被追问的地方。

Q20：RAG 的完整链路讲一下。

答：入库和检索两条链路。

入库：文档（PDF/TXT）→ 解析成纯文本 → 按 500 字分块、重叠 80 字 → 调 embedding 模型（通义 text-embedding-v4）转向量 → 写入 Chroma，metadata 里带来源文件名和分块序号。

检索：用户问题 → 向量化 → Chroma 相似度检索 top-k（rag_top_k=3）→把片段用分隔线拼成上下文 → 拼 prompt 让大模型"看着资料回答" → 资料里没有就明确说"未找到"。

追问：分块大小 500 字怎么定的？

  是个权衡。太小（比如 100 字）会丢上下文，一个完整的故障描述被切碎，模型拼不起来；太大（比如 2000 字）会稀释语义，检索出来的片段里大部分是无关内容，还挤占 prompt 长度。500 字是我按文档结构估的——我的故障文档一条大约 100~200 字，500 字能覆盖 2~3 条相关内容。重叠 80 字是为了避免答案正好被切在边界上。但我要诚实说：这个值我没有做过系统性调参对比，正确的做法是拿评测集跑chunk_size ∈ {200, 300, 500, 800} 看 Recall@3 的变化曲线。这是我下一步要做的。

Q21：你怎么测 RAG 的效果？（引出你的评测体系）

答：我建了一套评测集，分三层测——因为这三个指标混在一起测就不可解释了。

指标测哪一段为什么单独测
召回率只测检索器，不经过大模型混进模型后，你分不清是"没检索到"还是"检索到了但模型没说"
工具调用成功率 / 结果有效率Agent 执行工具的过程从日志埋点统计
问答准确率端到端最终答案用 LLM 做裁判打分

召回率的算法：我准备了 15 条"问题 → 期望命中的来源文件"的样本，检索 top-5，看期望文件有没有出现在结果里，算出 Recall@1 / @3 / @5，另外算 MRR（第一条命中结果的排名倒数）来反映排序质量。

实测结果：Recall@1 = 60%、Recall@3 = 80%、Recall@5 = 86.7%，MRR@3 = 0.700。

追问（关键）：那端到端的召回率呢？

  比 80% 低，而且我找到了原因。检索层 80% 是我直接调向量库测的。但走完整 Agent 链路时，模型会改写用户的 query 再传给 rag_summarize。比如用户问"扫地机器人日常保养要注意什么"，模型改写成了"智扫通Pro X1 日常保养注意事项"——它凭空加上了客户档案里的设备型号，而知识库里没有这个型号的表述，检索就落空了。

  这是个很重要的认知：检索层的指标不等于端到端体验。

  修法是两条：① 提示词里明确要求"query 用用户原话关键词，不要自己加限定词"；② 提示词里加铁律——"若 rag_summarize 返回未找到，必须如实告知，不许用你自己的知识补全"。第二条尤其重要，因为检索失败时模型会用自身知识编造答案，用户完全分辨不出来。

Q22：LLM 做裁判靠谱吗？你怎么保证评分可信？

答：不靠谱，所以我加了两层防线。

问题：我第一版纯用 LLM 裁判，结果发现一个典型的失效模式——系统回答是"根据现有知识库未找到相关信息"，裁判居然给了 1 分（通过）。因为参考答案里的知识点它"读到了"，就误以为回答覆盖了。

我的两层防线：

  1. 确定性规则兜底：回答为空、过短、或明确表示"未找到"时，直接判 0，不交给模型。
  2. 提示词里写死评分标准，明确列出"0 分"的情形（核心事实错误、答非所问、关键要点缺失、明显编造）。

追问：那 LLM 裁判还有什么局限？

  三个，我清楚：① 有位置偏差和宽容倾向，同样的答案换个顺序可能得分不同；② 样本量太小——我只有 10 条 agent 样本，连跑三轮结果是 70% / 30% / 50%，一条样本翻转就是 10 个百分点，这个波动完全掩盖了真实差异；③ 裁判模型和被测模型是同一个（都是 qwen3-max），存在自我偏好。

  我的改进计划：样本扩到每类 ≥30 条；抽 10% 人工复核校准裁判；有条件的话换一个不同厂商的模型当裁判。而且我在简历和文档里都会注明这是"LLM 裁判口径"，不冒充人工标注。

Q23：RAG 什么场景适用，什么场景不适用？

答：这是我认真想过的。

适合：知识密集、更新频繁、答案有明确出处、需要抑制幻觉的场景。比如产品手册问答、售后故障排查、内部制度查询。核心价值是把模型的"凭记忆回答"变成"看着资料回答"。

不适合：

  1. 需要精确计算或聚合的场景。RAG 本质是"找相似片段"，你问"上个月销售额是多少"，它可能检索到一段写着"销售额 120 万"的旧文档，给你一个过期的数字。这种必须走 Text2SQL——这也是我为什么在项目里同时做了这两条路。
  2. 强结构化查询。"查一下客户 ID 为 123 的订单"——这是主键查询，向量检索是在做"语义最近邻"，用在这里既慢又不准。
  3. 实时性要求极高的场景。文档入库有延迟（要解析、分块、向量化），如果数据每分钟都在变，RAG 跟不上。
  4. 答案需要跨多个文档推理的场景。top-k 检索是"捞回几个片段"，如果答案需要综合 10 个文档做多跳推理，单次检索覆盖不了，得用 Agent 迭代检索。

Q24：那你怎么决定一个问题走 RAG 还是走 Text2SQL？

答：我做了一个 data_router，四级分支：

  1. 先做数据集语义匹配：把用户问题和所有数据集的描述做 embedding 余弦，相似度超过阈值（text2sql_confidence_threshold=0.6）→ 走 Text2SQL；
  2. 结构化数据查不到 → 退回 RAG 知识库；
  3. 两者都没命中 → 礼貌澄清，引导用户换个说法；
  4. 预留工具分支。

追问：那在 Agent 里这套路由还有用吗？

  这里我要说清楚一个设计上的"两套并存"：data_router 是确定性路由，用在 /api/datasets/query 这个接口上，好处是可控、可解释、延迟低。而在 ReAct Agent 里，选哪条路由是交给模型决策的——模型看工具描述自己决定调 rag_summarize 还是别的。

  为什么不统一？因为两者的取舍不同：固定接口追求"稳定可预期"（客服点一下按钮就要确定的结果），Agent 追求"能处理开放问题"。如果非要统一，我会把 data_router 也包成一个工具给 Agent 调用，让模型决定什么时候用确定性路由。这是我下一步想做的。

六、高并发与部署篇

本篇 3 问：高并发改造清单、Nginx 层调优、Docker Compose 编排与依赖。注意区分「我做了」与「我知道但没做」，后者要主动说明取舍。

Q25：你这个项目做了哪些高并发改造？

答：先说我怎么理解这个项目的并发特征——不是 CPU 密集，是 IO 密集：

一个聊天请求要等：查 DB → 查向量库 → 调大模型（秒级流式）→ 可能再调地图 API。绝大部分时间在等外部 IO，CPU 基本闲着。所以优化方向不是"把 CPU 跑满"，而是在等 IO 的时候把事件循环让出去。

具体做了六件事：

  1. 全链路异步：FastAPI + async def + SQLAlchemy 2.0 异步 ORM + aiomysql 驱动。
  2. 连接池：pool_size=20, max_overflow=30, pool_pre_ping=True。
  3. 无状态可水平扩展：JWT 鉴权、session 不落地内存，多 worker + Nginx upstream 直接加机器。
  4. Celery 削峰：CSV 入库、向量化这种重任务异步化，前端轮询进度，不阻塞聊天主链路。
  5. 限流降级：Redis 令牌桶保护外部 LLM 和 DB。
  6. Nginx 层：upstream keepalive 复用连接、SSE 关缓冲、调大超时。

追问：那你知道这个架构的瓶颈在哪吗？

  知道，瓶颈一定在外部大模型的调用延迟和配额上，不在我这。我做过压测，后端 CPU 很低但 RT 很高，这就是典型的"外部依赖瓶颈"。这意味着两件事：① 我加机器提升不了单请求的响应速度，只能提升并发吞吐；② 真正的优化方向是缓存和降级——比如相同问题的答案缓存进 Redis，以及大模型不可用时降级到"只走 RAG 检索不做生成"。

  还有一个隐患：SSE 是秒级长连接，并发连接数会被放大。1000 个同时在聊的用户 = 1000 个挂着不动的连接。所以我调大了 worker_connections，也设了 proxy_read_timeout=300s——但"连接数上限"和"响应超时"之间的平衡我还没压测验证过。

Q26：Nginx 那层你具体调了什么？为什么？

答：三个关键配置，每个都有明确原因：

  1. proxy_buffering off（在 SSE 的 location 上）——这是最关键的。Nginx 默认会缓冲上游响应，攒够一批再转发。对普通接口没问题，但对 SSE 就是灾难：打字机效果没了，答案会憋着一次性蹦出来。同时我还让后端在响应头里加了 X-Accel-Buffering: no，双保险。
  2. proxy_read_timeout 300s——默认 60 秒。SSE 是长连接，模型生成慢的时候（比如长答案），60 秒会被 Nginx 掐断，用户聊到一半就断了。
  3. upstream 的 keepalive 32 + proxy_http_version 1.1 + proxy_set_header Connection ""——让 Nginx 和后端之间复用长连接，避免每个请求都重新三次握手。注意这三条必须一起配，只配 keepalive 是不生效的。

追问：还有别的坑吗？

  有一个运维上的坑，挺隐蔽的：重启 backend 容器之后，必须紧接着重启 nginx_gateway。因为 Nginx 在启动时会把 upstream 的 IP 解析并缓存下来，backend 容器重启后 IP 变了，Nginx 还往旧 IP 发请求，结果就是 502。后来我把它写进了操作手册里，避免别人踩。

Q27：Docker Compose 编排了哪些服务？依赖关系怎么处理？

答：六个服务：mysql / redis / backend / celery_worker / frontend / nginx_gateway。

依赖处理：depends_on 配合 condition: service_healthy——不是"容器起来了就走"，而是等 MySQL/Redis 真的能连上（健康检查通过）再启动后端。不然会出现"后端抢跑连不上数据库"然后一直重启的问题。

两个我特意处理的细节：

  1. Celery 容器的健康检查要单独写。它和 backend 用同一个镜像，会继承 Dockerfile 里"探测 8000 端口"的 HEALTHCHECK。但 Celery 根本不监听 8000，所以容器状态会永远显示 unhealthy——看起来像故障，其实一切正常。我改成了 Celery 官方的探活方式 inspect ping，顺带还能验证"worker 活着 + 能连上 Redis"。
  2. 镜像加速做成了可配置的。国内拉 Docker Hub 经常超时，我把所有镜像名写成 ${DOCKER_MIRROR:-}mysql:8.0 的形式，在 .env 里设一个变量就能全局切换加速源，不用改 compose 文件。

七、踩坑故事集（面试官最爱听的部分）

  每个坑都用 现象 → 排查 → 根因 → 修复 → 收获 讲。不要只讲"我改了一行代码"，要讲"我怎么想到去查那里的"。

坑 1：镜像构建成功了，但容器一直不健康

现象：docker compose build 成功，但 backend 容器起来后一直 unhealthy，日志报ImportError: cannot import name 'create_agent' from 'langchain.agents'。

排查：查依赖版本，发现 langchain 装成了 0.3.x。我的代码用的是 LangChain 1.x 的新 API create_agent，0.3.x 里根本没有这个函数。

根因：requirements.txt 里 langchain 相关的包有六个互相约束（langchain / langchain-core / langchain-community / langchain-chroma / langgraph / langchain-text-splitters），我当时随手升了一个，触发了 pip 的依赖重算，把 langchain 主版本降下去了。

修复：① 锁定一组经过 pip install --dry-run 验证过能共存的版本组合；② 在 Dockerfile 里加了构建期自检——docker build 阶段就跑一段脚本验证create_agent 和中间件 API 能否导入，不能就 sys.exit(1) 让构建失败。

收获："构建成功"不等于"能跑"。让错误尽量在构建阶段暴露，比等容器跑起来再查要便宜得多。这个自检后来真的又帮我拦过一次。

坑 2：一条错误消息把整条 SSE 流搞崩了

（详细内容见 Q14，这里是压缩版）

现象：问"广州天河区有哪些公园"，前端流到一半突然断掉。

排查：日志里 amap_around_search 参数校验失败（缺 location），紧接着 DashScope 报 400 The "function.arguments" parameter must be in JSON format。

根因：错误消息里内嵌了 Python 字典字面量 {'keyword': '公园'}（单引号），模型下一轮模仿这个格式生成工具参数，产生非法 JSON。

修复：中间件回灌错误消息前，用正则把花括号片段剔除。

收获：给模型的上下文是"脏"的，模型的行为就会"脏"。错误消息也是上下文的一部分，不能直接把异常原文丢给模型。

坑 3：向量库入库成功了，Agent 却说"没找到"

现象：入库脚本日志显示成功，单独写脚本检索也能查到内容，但走 HTTP 问 Agent，一律回答"根据现有知识库未找到相关信息"。

排查：我一开始怀疑是 embedding 的问题，但单独跑脚本明明能查到。后来意识到——单独跑脚本是"新进程"，走 HTTP 是"后端进程"，两者的区别在于谁先初始化了 Chroma。

根因：我的入库脚本用了 reset_collection()，它会删除并重建整个 collection。而正在运行的后端 worker 手里已经持有的 collection 句柄，指向的是一个已经被删掉的集合。所以它的检索永远返回空。

修复：改成按 id 逐条 delete(ids=...)，collection 本身不变，其它进程无需重启。

收获："脚本能跑通"和"服务能跑通"是两回事。排查这类问题时，第一个要问自己的是"这个进程是什么时候启动的、它手里持有什么状态"。

坑 4：容器里的路径全部指错了地方

现象：向量库、上传文件、日志，容器一重建就全丢了。查下来发现它们都写到了/data 和 /logs，而 compose 挂载的是 /app/data 和 /app/logs。

排查：看 config.py 里的 PROJECT_ROOT = Path(__file__).resolve().parent.parent.parent。宿主机布局是 backend/app/config.py，上溯三级正好是项目根；但容器里是 /app/app/config.py（Dockerfile 用 COPY app/ ./app/），上溯三级得到的是 /，越界了。

修复：改成探测式判定——上溯三级后看有没有 docker-compose.yml 或 backend/ 目录，没有就回退两级。

收获：__file__ 的相对层级在容器里会变。凡是"根据文件位置推算项目根"的代码，都要考虑容器内的目录结构。

坑 5：前端一个"空白气泡"

现象：用户提问后，AI 气泡一直是空的，毫无反应，也没有任何报错。

根因：后端出错时会推一个 {"error": "..."} 帧（没有 content 字段）。前端只读了 parsed.content，这一帧被静默丢弃了；紧接着的 [DONE] 触发 onDone，把 isStreaming 置为 false，流就结束了——于是留下一个永远空白的气泡。

修复：前端 SSE 解析里显式处理 error 帧，调用 onError 回调并显示错误信息。

收获："错误没有进入错误分支"是最难查的一类缺陷——它不报错、不打日志，静态读代码也很难发现。只要定义了协议帧，就必须把每一种帧都处理到。

八、场景适用性与边界

本篇 2 问，考的是判断力而不是记忆力：这套系统适合什么场景、不适合什么场景，以及如果重来会怎么改。

Q28：这套系统适合什么场景？不适合什么？

适合：

  • 知识密集 + 有明确出处的问答（售后、产品手册、内部制度）——RAG 能压制幻觉
  • 需要"自然语言查业务数据"的场景——Text2SQL 让非技术人员也能查库
  • 需要调用外部服务的客服——工具调用把地图、天气、订单系统统一进一个入口
  • 需要记住用户偏好的长期服务——长期记忆让体验有连续性

不适合：

  1. 高并发短请求场景（比如秒杀、纯查询 API）。这个架构是给"秒级长连接 + 重外部依赖"设计的，拿来做高频短请求是错配，此时 SSE 和 Agent 都是纯开销。
  2. 强合规、答案必须 100% 准确的场景（医疗诊断、法律意见）。LLM 的幻觉是原理性的，RAG 只能降低不能消除。这种场景必须有人工复核环节。
  3. 超低延迟场景（要求 100ms 内响应）。一次 LLM 调用就是秒级，这个架构从根上不匹配。
  4. 离线/内网无 GPU 的场景。依赖外部大模型 API，没网就没法用。

Q29：如果让你重新设计，你会怎么改？

答：四个方向，按优先级：

1. 评测体系先建，功能后做（最大的反思）我是先把功能做完才补评测的，结果发现"工具调用成功率 100%"这种假指标骗了我很久。正确的顺序是先建评测集和埋点，再开发——这样每次改动都能立刻知道是变好还是变坏。而且我的评测集只有 10~15 条，波动大到掩盖真实差异。

2. Agent 的可观测性升级现在只有日志。应该上 OpenTelemetry + LangSmith 这类 trace 工具，把一次 Agent 执行的完整链路（每个节点的输入输出、耗时、token 消耗）可视化。现在排查问题靠翻日志，效率低。

3. 成本与延迟优化

  • 缓存：相同/相似问题的答案缓存进 Redis（注意要按 customer_id 隔离，因为答案依赖客户档案）
  • 模型分级：简单问题用小模型（qwen-turbo），复杂问题才上 qwen-max
  • RAG 前置过滤：不是所有问题都需要检索，可以先做一次轻量分类

4. 安全加固python_func 那个 exec 沙箱要关掉；Text2SQL 现在靠关键字黑名单，应该换成数据库层面的只读账号 + 白名单视图，从权限上根治。

八·五、通用后端基础题（必问，用项目回答最有说服力）

本篇 6 问，是通用后端基础题：GIL、await 底层、SSE 与 WebSocket 的区别、Redis 的角色、事务隔离级别、外部依赖挂掉后的兜底。每一题都用本项目作答，避免背教科书。

Q33：Python 的 GIL 是什么？对你的项目有什么影响？

答：GIL 是 CPython 的全局解释器锁——同一进程内，同一时刻只有一个线程在执行 Python 字节码。

对我项目的影响，分两种情况说：

  • IO 密集（我的主场景）：GIL 影响不大。因为线程在等网络 IO 时会主动释放 GIL，别的线程能接着跑。我的请求 90% 时间在等大模型/DB，所以异步 + 单进程能扛住不少并发连接。
  • CPU 密集：GIL 会把多线程串行化，多线程完全没用。这时候要么开多进程（我就是用 uvicorn --workers 2），要么丢给 Celery。

所以我的策略是：IO 用 async/await，CPU 密集任务（CSV 解析、向量化）丢 Celery 多进程跑。这不是"为了用异步而用异步"，是被 GIL 这个约束推出来的设计。

追问：那 asyncio.to_thread 是干什么的？

  用来把阻塞的同步调用丢到线程池，避免它卡住事件循环。我项目里有两个地方用了：Chroma 的 add_documents 和 similarity_search——它们是同步方法，直接在 async def 里调会阻塞整个事件循环，所以用 asyncio.to_thread 包一层，让主线程能继续处理别的请求。

Q34：await 的时候底层发生了什么？

答：await 一个协程/IO 操作时，当前协程会把控制权交还给事件循环，事件循环去执行其它就绪的任务；等这个 IO 完成了，再把控制权还回来。

关键认知：await 本身不创建线程、不创建进程，它是单线程内的协作式调度。所以有个铁律——在 async def 里不能有阻塞调用。只要有一行同步的耗时操作（同步 DB 驱动、time.sleep、CPU 密集计算），整个事件循环就会被卡住，所有并发请求一起卡。这就是我前面说的为什么要用 asyncio.to_thread。

追问：那怎么发现"异步里混了阻塞调用"？

  症状是"并发上不去，CPU 也不高"。排查手段：① 看事件循环的 lag（asyncio 可以挂一个监控 task 测量调度延迟）；② 代码 review 时专门搜同步库的调用（比如 requests、同步的 pymysql、time.sleep）；③ 压测时观察"QPS 上不去但 CPU 很闲"，基本就是这个原因。

Q35：SSE 和 WebSocket 有什么区别？你为什么选 SSE？

答：核心区别是通信方向和协议复杂度：

SSEWebSocket
方向单向（服务端→客户端）双向
协议就是普通 HTTP，text/event-stream需要 HTTP Upgrade 握手，独立协议
自动重连浏览器原生支持要自己实现
二进制不支持（只能文本）支持
代理/网关兼容性好（就是 HTTP）部分老代理会掐断

我选 SSE 的原因：我的场景是"用户问一句 → 服务端流式回答"，本质就是单向推送，不需要双向通信。用 WebSocket 属于杀鸡用牛刀——还要自己实现心跳、重连、消息分帧。

追问：那 SSE 有什么缺点？

  三个：① 只能服务端推，如果以后要做"用户在生成过程中打断/追问"，SSE 得再发一个 HTTP 请求；② 浏览器对同域 SSE 连接数有限制（HTTP/1.1 下大约 6 个），多标签页同时开会受影响——上 HTTP/2 能解决；③ 只能传文本，二进制要 base64 编码。

  顺便说个坑：EventSource 这个原生 API 不支持自定义请求头，所以带不了 Authorization。我最后是用 fetch + ReadableStream 手动解析 SSE 的。

Q36：Redis 在你项目里承担什么角色？

答：三个角色，每个都对应具体的业务需求：

  1. Celery 的 broker 和 result backend——用 db1 做任务队列，db2 存任务结果。CSV 入库、向量化这种重活丢进去异步跑。
  2. 限流计数器——基于令牌桶，保护外部大模型配额和 DB。
  3. 缓存——接口缓存。

配置上我做了两件事：

  • --appendonly yes 开 AOF 持久化，容器重启不丢任务（不然队列里的任务就没了）
  • --maxmemory 256mb --maxmemory-policy allkeys-lru，内存满了淘汰最久未用的 key。这个策略是缓存场景的标准选择——如果是当数据库用，就得用 noeviction 然后报错，而不是静默丢数据。

追问：为什么 Celery 不用 asyncio 直接跑？

  因为 Celery 任务和 Web 请求的生命周期、可靠性要求完全不同：① Web 请求失败了用户重试就行；Celery 任务需要重试、需要持久化队列、需要结果回查，asyncio 裸跑这些都没有；② 任务可能跑几分钟（CSV 解析 + 向量化），放在 Web 进程里会占着 worker；③ 任务要能独立扩容——CSV 导入高峰期我可以单独多起几个 Celery 容器，不用动 Web 层。

Q37：数据库事务隔离级别了解吗？你的项目用的哪个？

答：MySQL InnoDB 默认是 RR（可重复读），我用的就是默认值。

四个级别：读未提交（脏读）→ 读已提交（不可重复读）→ 可重复读（幻读，InnoDB 用间隙锁基本解决）→ 串行化。

为什么我没改：我的业务里没有强依赖"读到最新提交"的场景。会话、消息都是"自己写自己读"，客户档案基本不变更。RR 的代价是并发写入时锁范围更大，但我的写入量很低（主要是追加消息），所以没成为瓶颈。

追问：那你项目里有没有需要事务的地方？

  有，而且我处理了。最典型的是"保存用户消息"和"保存助手消息"：用户消息在流开始前落库并 commit，助手消息在流结束后落库并 commit。我没有把两件事放在一个事务里，因为流可能持续几十秒——如果开一个大事务，会长时间持有行锁，还可能把连接池占满。

  另一个例子是数据集上传：我先 flush() 拿到自增 ID，再把数据集和任务记录一起 commit，保证 Celery worker 一启动就能查到 async_tasks 记录。如果分两次 commit，会出现"任务已经在跑但记录还不存在"的竞态。

Q38：如果外部大模型服务挂了，你的系统会怎样？

答：这是我专门设计过的一层——降级路径。

api/chat.py 里有一个 _friendly_error()，把上游异常翻译成用户能看懂、能照做的一句话：

  • Arrearage（欠费）→ "大模型账户欠费，请到百炼控制台充值，到账后直接重发即可，无需重启服务"
  • Throttling（限流）→ "请求过于频繁，请稍等几秒后重试"
  • InvalidApiKey → "API Key 无效，请检查 .env 配置"
  • Timeout → "调用大模型超时，请稍后重试"

为什么要做这层翻译：上游的报错是给开发者看的（request_id: xxx status_code: 400 code: Arrearage），直接推到前端，用户既看不懂也不知道该干什么。

追问：那为什么不做得更彻底，比如自动降级到"只检索不生成"？

  因为这会带来更糟的体验。 检索出来的是一堆原始文档片段，直接甩给用户等于"你自己看吧"，反而不如老实说"服务暂时不可用"。我的判断是：能明确告知的失败，好过含糊的降级。如果真要做降级，我会做成"返回检索到的原文 + 明确标注这是未经整理的资料"，而不是让用户误以为这是完整答案。

九、压力问题应对

本篇 3 问，全部是压力型问题：项目是不是你一个人做的、最大的不足是什么、问到不会的怎么办。这一章考的是姿态，不是知识。

Q30：这个项目是你一个人做的吗？做了多久？

  独立完成的。时间上分两段：原型版先把链路跑通，v2 重构花了主要精力在工程化上——异步改造、容器编排、评测体系、以及修那些只有跑起来才会暴露的坑。我最有收获的反而不是写功能，是排查那几个"看起来正常但其实错了"的问题，比如工具成功率 100% 那个假指标。

Q31：你觉得自己这个项目最大的不足是什么？

  三个，我不回避：① 评测样本太少，导致指标不可信，这是最该先补的；② 没有真正的生产流量验证，我的并发设计是"按原理做的"，没有经过真实压测调优，连接数上限、超时阈值这些参数都还是经验值；③ Text2SQL 的安全靠应用层黑名单，这是"防君子不防小人"的做法，真正的解法是数据库权限隔离，这块我知道该怎么做但还没做。

Q32：如果面试官问到你不会的怎么办？

模板：

  "这块我确实没有深入做过。但我可以讲一下我的理解边界——我知道它大概解决什么问题（说你能说的部分），具体到（他不问的那个细节）我没有实践过，不敢乱说。如果让我做，我会先去查官方文档的 X 部分，然后用一个小 demo 验证。"

关键：明确划出"我知道什么、不知道什么"的边界，比含糊地糊过去要可信得多。面试官对"知道自己不知道"的容忍度，远高于"不懂装懂"。

十、反问面试官

面试最后一定会让你提问。问这三个，能反过来体现你的水平：

  1. "团队现在的 AI 能力是已经上线在跑，还是在探索阶段？如果是探索阶段，你们现在最头疼的是效果不可控还是成本/延迟？"（→ 表明你知道 AI 落地的真实难点在哪）
  1. "后端这块，团队现在更关注稳定性还是吞吐量？有没有在用可观测性工具（trace/metrics）？"（→ 表明你有工程化意识，不只是写业务代码）
  1. "如果我进来，前三个月你希望我先补哪块能力？"（→ 表明你愿意对齐预期，而不是只想表现自己）

不要问：加班多不多、能不能远程、涨薪机制（这些留到 HR 面）。
